# 根幹のルール

何かを足したくなったとき、まず次の問いに答える。

## 制約には 2 種類ある

- **正しさを守る制約**: 落とすと壊れるもの。rename の原子性、`mkdir -p` の禁止、古いロックを消さない、など。これは残す
- **予測を守る制約**: 「将来こういう使い方をするはず」という見込みを守るもの。プロトタイプの repo キーの hash、step を root だけが進める規則、フォージの略号などがこれだった。予測が外れるたびに制限が足かせになり、外しても設計の跡が残った

lsboard に残っているのは前者だけである。新しい規則を足すときは「これはどちらか」を問い、後者なら足さない。予測が要るなら、まず使ってみてから決める。

## 核になる規則

それぞれ 1 行の理由を添える。理由が消えたら規則も消してよい。

- **ファイルシステムが正本である。** DB もデーモンも持たないので、`ls` と `mkdir` と `mv` があれば読み書きできる
- **ファイル名が正本で、更新は rename だけ。** 本文を読み書きしないので、read-modify-write の競合が起きない
- **`ls` で読める。entry 以外は `.` で始める。** 人がそのまま見られることが最大の価値で、整形コマンドは補助にすぎない
- **自分の entry 以外を書かない。** 他人への依頼や承認は board の外で渡す。サブエージェントの entry は、それを動かしているセッションの hook が書く
- **hook はエージェントを止めない。** 常に終了コード 0 で終わり、失敗は stderr に出す。板の不整合よりエージェントの停止のほうが害が大きい
- **迷ったら解除しない。** 処理中なのに待ちと出るほうが、待っているのに処理中と出るより害が小さい
- **エージェントの宣言は hook が触らない。** `lsboard set waiting` で付けた待ちを解除するのは、人のプロンプト送信だけ
- **古いロックを自動で消さない。** 消す判断が同時に起きるとロックを二重に取れてしまう。lint が報告し、人が消す
- **デーモンは正本を持たない。** `wait` と `watch` は読み手であり、落ちても board は無事で、再起動すれば `ls` 1 回で追いつける
- **規約は依存ゼロ、実装は参考。** 仕様（[spec.md](spec.md)）はシェルだけで守れる。Rust のバイナリは参考実装で、別言語の書き手が同じ board に書いてよい

## 効率の原則

親エージェントのトークン消費を減らすための規則。核になる規則と同じ重みで扱う。

- **待つのはブロッキングで、LLM を巻き込まない。** `lsboard wait` はプロセスとして眠る。親は 1 回のツール呼び出しを置くだけで、待っている間のトークンはゼロ
- **届けるのは注意が要る遷移だけ。** `waiting` `idle` `ended` への遷移と、新しく現れた entry。`working` と `background` の行き来は届けない
- **まとめて 1 通、1 子 1 行。** 1 秒の時間窓に起きた変化は 1 回の出力にまとめ、同じ sid の変化は最新の 1 行にする。親が `ls` をやり直さずに判断できる
- **hook は軽い。** ネイティブバイナリで JSON を読んで rename するだけ。1 回あたり数ミリ秒
- **注入は最小限。** セッション開始時に context へ入れる説明は 5 行
